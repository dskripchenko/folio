# ADR-007. Ресурсы приложения, журнал работы, лимиты памяти, запрет сна

- Статус: принято автором 2026-11-05; E1–E5 выполнены, выпуск — folio 1.11.0
- Отступления от плана: форматтеры в «Процессах» не показываются (живут доли секунды, замер раз в 2–15 с их не застаёт); помощники Chromium (сеть, хранилище) из окна не завершаются — без них folio не работает; на Windows замер — один вызов PowerShell (CIM) за замер, без долгоживущего процесса; ошибки окна берутся из `console-message` главного процесса, без своего канала из preload
- Дата: 2026-11-05
- Повод: в folio 1.10.0 и раньше git status копился в очередь, пока агент писал
  файлы. Главный процесс доходил до 13–15 ГБ и ~400% CPU, после чего macOS
  глушил приложение. Исправлено в 1.10.1. Но человек узнал об этом только по
  тормозам всего ноутбука, а расследовать пришлось по системным отчётам
  macOS (`DiagnosticReports/*.cpu_resource.diag`, `*.ips`): своих журналов у
  folio нет.

## Цели

1. Видеть, сколько памяти и процессора занимает folio вместе со всем, что он
   запустил: окна, языковые серверы, терминалы, форматтеры.
2. Вести журнал работы с ротацией: по нему разбираются сбои и утечки, в том
   числе задним числом.
3. Задавать лимит памяти. Приложение не должно тихо разрастаться до
   десятков гигабайт.
4. Не давать системе уснуть, как Amphetamine, на всех трёх ОС. Главный
   сценарий: агент работает в консоли folio, а человек отошёл.

## Устройство

### M1. Монитор ресурсов (`src/main/resources.ts`)

- Источник для процессов Electron (главный, окна, GPU, utility):
  `app.getAppMetrics()`. Он кроссплатформенный и отдаёт CPU % и рабочую память
  по каждому процессу.
- Дочерние процессы folio: pty-оболочки (`pty.ts`), LSP (`lsp/manager.ts`),
  форматтеры (`format.ts`). Их pid известны. Для каждого считаются он сам и
  его потомки: агент в терминале — потомок оболочки, его стоит видеть
  отдельной строкой «в консоли N». Без зависимостей:
  - macOS/Linux: `ps -A -o pid=,ppid=,rss=,%cpu=`, один вызов на всё дерево;
  - Windows: `Get-CimInstance Win32_Process` (WorkingSetSize, ParentProcessId)
    плюс разница `KernelModeTime + UserModeTime` между замерами для CPU.
- Замер раз в 2 с, пока открыта панель, иначе раз в 15 с (для журнала и
  лимитов). Сам замер дешёвый, в отдельной очереди, без наложения: правило
  из 1.10.1.
- **Строка состояния**: `◔ 1,2 ГБ · 8%` по всему folio. Цвет меняется у
  мягкого лимита. По щелчку открывается панель.
- **Панель «Процессы»** (как диспетчер задач Chrome): строки «Главный»,
  «Окно», «GPU», «LSP: intelephense», «Консоль 2 (zsh → claude)»,
  «Форматтер». Колонки: память, CPU, время работы. Действия:
  перезапустить LSP, закрыть консоль, завершить процесс (с подтверждением).
  Внизу график памяти за последние 30 мин: утечку видно по наклону.
- Кучу JS главного процесса показывает `process.memoryUsage()`, кучу окна —
  `performance.memory`. Это отдельная строка подсказки: «куча / всего».

### M2. Журнал (`src/main/log.ts`)

- Свой логгер, без electron-log. Файлы `folio-data/logs/folio-YYYY-MM-DD.log`,
  по одной строке JSON (`ts, level, proc, area, msg, data`). Запись буферится
  и сбрасывается раз в секунду и при выходе.
- **Ротация**: при запуске и раз в сутки удаляются файлы старше N дней
  (настройка, по умолчанию 5, диапазон 1–30). Один день ограничен 50 МБ: при
  переполнении файл получает суффикс `.1` и пишется дальше; уровень `debug`
  отбрасывается первым.
- Что пишется:
  - запуск и выход, версия, ОС, путь данных, открытые проекты (только число);
  - `uncaughtException`, `unhandledRejection` в главном процессе; ошибки окна
    через IPC (`window.onerror`, `unhandledrejection`, `console.error`);
  - `render-process-gone`, `child-process-gone`, `app.on('gpu-process-crashed')`;
    выход LSP, pty и форматтеров с кодом;
  - **замер ресурсов раз в минуту** (M1) по процессам: по нему видно, когда
    и что начало расти;
  - медленные операции: git, поиск, индекс, PDF дольше 2 с; длина очередей;
  - срабатывания лимитов (M3) и запрета сна (M4).
- Аварийные дампы: `crashReporter.start({ uploadToServer: false })`, дампы
  лежат в `folio-data/crashes/` и чистятся той же ротацией.
- Содержимое файлов, тексты и токены в журнал не попадают. Пути пишутся
  относительными к проекту.
- Меню «Справка → Открыть журнал» и «Собрать отчёт»: zip с журналами за 3
  дня, дампами и версией, для передачи.
- MCP: инструмент `get_app_log` (последние N строк, фильтр по уровню). Агент
  сможет сам посмотреть, что не так с folio.

### M3. Лимиты памяти (`src/main/limits.ts`)

Жёсткий предел V8 (`--max-old-space-size`) — плохая основная мера: на
пределе процесс падает с OOM и теряет несохранённое. Поэтому лимиты
двухуровневые:

- **Мягкий лимит** (настройка, по умолчанию 4 ГБ на весь folio, или «выкл»).
  При превышении:
  1. запись в журнал с замером по процессам;
  2. разгрузка: сброс кэшей индекса файлов и символов, буферов прокрутки
     скрытых консолей сверх 5 тыс. строк, `session.clearCache()` окна,
     перезапуск самого тяжёлого LSP;
  3. если не помогло за минуту — уведомление: «folio занимает 5,1 ГБ, больше
     всего — LSP intelephense (3 ГБ). [Перезапустить его] [Перезапустить
     folio] [Открыть процессы]». Несохранённое переживает перезапуск через
     буферы (`buffers.ts`).
- **Жёсткий предел кучи** (дополнительная настройка, по умолчанию выкл):
  `js-flags=--max-old-space-size=N` для окон через
  `app.commandLine.appendSwitch` до `ready`. Для главного процесса —
  перезапуск самого себя с флагом (`app.relaunch({ args })`) при изменении
  настройки. Применяется после перезапуска, это сказано рядом с настройкой.
- **Лимит на дочерние процессы**: для LSP на Node (intelephense,
  typescript-language-server, vscode-*) — `NODE_OPTIONS=--max-old-space-size`
  при запуске; для остальных — только контроль M1: при превышении своего
  лимита (по умолчанию 2 ГБ) LSP перезапускается с записью в журнал.
- Агент в консоли под лимит folio **не попадает**: это чужая программа. Он
  показан в панели, но не перезапускается и не учитывается в сумме для мягкого
  лимита (учитывается отдельно, только для показа).

### M4. Не засыпать (`src/main/awake.ts`)

Кроссплатформенно это делает Electron:
`powerSaveBlocker.start('prevent-app-suspension' | 'prevent-display-sleep')`.
Внутри это IOPMAssertion на macOS, `SetThreadExecutionState` на Windows и
inhibit через D-Bus (ScreenSaver / logind) на Linux. Своей нативщины не нужно.

- Режимы: **«Не засыпать»** (система не спит, экран может гаснуть) и **«Не
  гасить экран»**.
- Длительность: до выключения, 1 ч, 2 ч, 4 ч, до времени.
- **Пока работает агент** — то, чего нет у Amphetamine: пока в любой консоли
  folio идёт программа (по shell integration: команда начата и не закончена)
  или вывод был за последние N минут. Плюс «пока идёт задача» (`tasks.ts`).
- Где включается: значок в строке состояния (чашка), меню консоли «Не
  засыпать, пока идёт команда», палитра команд, меню в Dock/трее. Состояние
  видно всегда, пока блокировка действует.
- Ограничения, о которых сказать честно в доках:
  - **macOS, закрытая крышка**: обычная блокировка от сна при закрытой
    крышке не спасает (без внешнего монитора и питания). Amphetamine
    обходит это отдельным привилегированным помощником. В folio этого не
    делаем, по крайней мере в первой версии.
  - Linux: зависит от окружения рабочего стола (GNOME/KDE поддерживают; в
    голом WM может не работать). Если inhibit не взялся, это пишется в журнал
    и показывается в подсказке.
  - Блокировка снимается при выходе из folio; после сбоя её держать некому.

## Этапы

| Этап | Что | Почему в этом порядке |
|---|---|---|
| E1 | M2 журнал + замер раз в минуту | Нужен первым: всё остальное в него пишет, и он сразу помогает с жалобами |
| E2 | M1 строка состояния + панель «Процессы» | Видно, кто ест |
| E3 | M3 мягкий лимит + лимиты LSP | Опирается на замер M1 |
| E4 | M4 не засыпать, включая «пока работает агент» | Независим, можно параллельно с E2 |
| E5 | Жёсткий предел кучи, «Собрать отчёт», MCP `get_app_log` | Дополнения |

Каждый этап — отдельный PR с unit и e2e, доки en/ru/de/zh. Релиз 1.11.0 после
E1–E4 или по этапам, на выбор автора.

## Решения автора

| № | Вопрос | Решение |
|---|---|---|
| 1 | Срок хранения журнала | **5 дней** по умолчанию (настройка 1–30) |
| 2 | Мягкий лимит | **4 ГБ** по умолчанию |
| 3 | Агент в консоли | **Отдельно**: показан, в сумму folio и в лимит не входит |
| 4 | Закрытая крышка на macOS | **Без помощника**: не поддерживается, сказано в доках |
| 5 | Релиз | **Одним 1.11.0** после E1–E5 |

## Риски

- Замер `ps` / CIM на Windows сам стоит ресурсов. Отсюда частота 15 с в фоне
  и CIM одним запросом. На Windows `Get-CimInstance` медленный (~300 мс):
  держать один долгоживущий PowerShell и не запускать его на каждый замер.
- Мягкий лимит, сбрасывающий кэши, может сделать поиск и переходы медленнее
  на время перестроения индекса. Это пишется в уведомлении.
- Журнал не должен стать утечкой сам: буфер с потолком, при переполнении
  строки отбрасываются со счётчиком «пропущено N».
